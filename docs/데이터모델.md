# wewant 데이터 모델 명세 (v2, 2026-11-13 확정)

원본 자료(`테이블 설명.txt`, `필드변수 설명.txt`, 예시 엑셀)를 바탕으로 하되, 이 문서가 우선한다.
Prisma 스키마는 이 문서를 그대로 옮겨 작성한다. DB 테이블·필드 이름은 아래 표기를 유지한다.

## 공통 규칙
- 고유코드는 `접두문자 + 5자리 숫자`(권한만 2자리) 형식을 유지하고 DB가 자동 채번한다.
- y/n 값은 boolean으로 저장한다. 필드명은 `_activ`로 통일한다(`dept_active` → `dept_activ`).
- 모든 테이블에 `created_at`, `updated_at`을 둔다.
- **삭제는 비활성화로 처리한다.** 위촉 이력이 끊기면 연임·재임기간 계산이 깨진다.
- 날짜 필드는 시간 없는 날짜(date)로 저장한다.

### 구현 방식 (1단계, `prisma/schema.prisma`)
- 자동 채번: 테이블마다 PostgreSQL 시퀀스(`tb_dept_seq` 등)를 두고 PK 기본값을 `'d' || lpad(nextval, 5, '0')`로 만든다. `auth_id`는 직접 입력, `log_id`는 자동 증가 정수.
- 선택값(`국소/부서`, `당연직/위촉직` …)은 PostgreSQL enum으로 저장하며 DB 값은 한글이다. Prisma 코드에서는 영문 이름(`GUKSO` 등)을 쓰고 한글 표기는 `src/lib/enum-labels.ts`로 변환한다.
- 모든 외래키는 삭제 제한(`RESTRICT`). 참조 중인 행은 DB가 삭제를 거부한다.
- 검색용 인덱스: 각 외래키, `TB_Person(person_name, birth_date)`(동명이인 확인), `TB_AuditLog(target_table, target_id)`.

### 예시 엑셀 시드 변환 (`prisma/seed.ts`)
- `TB_User.login_id`는 엑셀에 없어 `user_id`와 같은 값으로 넣고 `must_change_pw = true`.
- `TB_Appoint.appoint_kind`는 모두 `신규`.
- `expire_due`: 당연직은 null, 위촉직은 엑셀 종료일을 쓰지 않고 "위촉일 + 임기년수 − 1일"로 다시 계산.
- `appoint_end`: 엑셀 종료일이 시드 실행일 이전이면 실제 해촉일로 저장하고 `end_reason = 기타`, 미래 날짜면 null.

| dept_id | `d00001` PK | |

부모가 없는 `부서`(사업소 4곳)는 국소별 통계에서 "사업소" 묶음으로 표시한다.

관리 규칙 (3단계, `src/lib/rules/master-rules.ts`):
- 국소는 상위 부서가 없다. 부서의 상위는 활성 국소이거나 없음(사업소). 자기 자신은 상위가 될 수 없다.
- 활성 하위 부서가 있는 국소는 부서로 바꿀 수 없다.
- 활성 하위 부서·소속 활성 사용자·소관 활성 위원회가 하나라도 있으면 비활성화할 수 없다.
- 상위 국소가 비활성이면 다시 활성화할 수 없다.

사용자 관리 규칙 (3단계):
- 계정 발급·비밀번호 초기화 시 임시 비밀번호(12자)를 화면에 한 번만 보여 주고 `must_change_pw = true`로 둔다. 초기화·비활성화하면 그 사용자의 세션을 모두 지운다.
- 본인은 비활성화하거나 총괄 권한을 내릴 수 없다. 활성 총괄은 최소 1명 남아야 한다.
- `login_id`는 발급 후 바꾸지 않는다(`email`이 여기서 만들어지므로).

### 로그인 테이블 (2단계, Better Auth가 관리)
TB_User가 Better Auth의 사용자 테이블을 겸한다(`src/lib/auth.ts`에서 필드 연결). 아래 3개는 Better Auth가 읽고 쓰며 앱 코드가 직접 고치지 않는다.

| 테이블 | 용도 | 주요 필드 |
|---|---|---|
| TB_Session | 로그인 세션 (8시간, 사용 중이면 연장) | id, token(고유), user_id → TB_User, expires_at, ip_address, user_agent |
| TB_Account | 로그인 수단. 아이디·비밀번호는 `provider_id = credential`, `password`에 해시 | id, account_id, provider_id, user_id → TB_User, password 등 |
| TB_Verification | 일회용 인증값 (내부용) | id, identifier, value, expires_at |

- 이 3개 테이블의 PK는 무작위 UUID다(업무 데이터가 아니므로 접두문자 코드를 쓰지 않음).
- Better Auth는 PK의 코드상 이름이 `id`여야 해서 TB_User만 Prisma 필드명이 `id`이고 DB 컬럼은 `user_id` 그대로다.
- 세션은 로그아웃·만료·비밀번호 변경 시 Better Auth가 행을 지운다(업무 데이터가 아니므로 "삭제는 비활성화" 규칙의 예외).
- 비활성 사용자는 세션을 만들 수 없고, 로그인 중 비활성화되면 다음 요청에서 세션이 모두 지워진다.

## 직위 변경 규칙 (같은 인물이 위원회마다 다른 직위로 표시되는 문제)

상황: 홍길순이 A위원회에는 "한림대 컴퓨터공학과 교수"로, B위원회에는 "한림대 산학협력단 부단장"으로 위촉되어 있다. B위원회 담당자가 부단장을 단장으로 바꿔도 A위원회 표시는 그대로여야 한다.

구조:
```
TB_Person  홍길순 (1행)
   ├─ TB_Pos a1: 한림대 컴퓨터공학과 / 교수      ← A위원회 위촉 건이 참조
   ├─ TB_Pos a2: 한림대 산학협력단 / 부단장      ← (변경 전) B위원회 위촉 건이 참조
   └─ TB_Pos a3: 한림대 산학협력단 / 단장        ← (변경 후) B위원회 위촉 건이 참조
```

규칙:
1. 위촉 건은 인물이 아니라 **인물의 특정 소속직위 행(pos_id)** 을 가리킨다. 위원회마다 다른 행을 가리킬 수 있다.
2. 위원회 화면의 "소속직위 변경"은 **TB_Pos 행을 고치지 않는다.** 해당 인물의 소속직위 목록에서 다른 행을 고르거나 새 행을 추가한 뒤, **그 위촉 건의 pos_id만 교체**한다.
3. 따라서 B위원회의 변경은 B의 위촉 건 한 행만 건드리고, A위원회 위촉 건(a1 참조)에는 영향이 없다.
4. 교체 후 어떤 위촉 건도 참조하지 않게 된 행(a2)은 `pos_activ = false`로 바꾼다. 과거 이력 조회를 위해 삭제하지 않는다.
5. 변경 전·후 pos_id는 TB_AuditLog에 남긴다.
6. TB_Pos 행 자체의 글자 수정(오타 정정)은 총괄, 또는 그 행을 참조하는 위촉 건이 모두 본인 소관인 담당자만 할 수 있다.
7. 이것은 "소속기관의 직위"가 바뀐 경우다. "위원회 내 직위"(위원→위원장)가 바뀐 경우는 `appoint_kind = 직위변경`으로 기존 건을 종료하고 새 건을 만든다.

## 계산 규칙 (저장하지 않고 계산)

| 값 | 계산 |
|---|---|
| 임기만료 예정일 기본값 | `appoint_start + term_yr년 − 1일`. 예: 2026-10-01 위촉, 임기 2년 → **2028-09-30**. 보궐 등은 직접 수정 가능 |
| D-day | `expire_due − 오늘` |
| 만료 알림 대상 | 재임 중 + 위촉직 + D-day가 60 이하. 내 소관 위원회만 홈에 표시 |
| 연임횟수 | 같은 위원회·같은 인물의 위촉직 건 중 `appoint_kind = 연임` 건수 |
| 연임 가능 여부 | 연임횟수 < `reappoint_num` |
| 직위별 재임기간 | 같은 위원회·같은 인물의 건을 appos_id별로 묶어 기간 합산 |
| 현원 / 정원 | 재임 중 건수 / `member_cap` |
| **위촉직 중복 수** | 인물 기준, 활성 위원회에서 재임 중인 **위촉직** 건수. **당연직은 세지 않는다** |

## 중복위촉 처리 (차단하지 않고 경고)
- 조례상 위촉직은 3개까지 허용되나 예외가 있으므로 **입력을 막지 않는다.**
- 위촉직 중복 수가 **4 이상인 인물**은 위원 명부, 위원 조회, 중복위촉 조회 화면에서 이름 옆에 경고 아이콘을 표시하고, 아이콘에 "위촉직 N개 위원회 중복 위촉"과 위원회 목록을 보여준다.
- 신규 위촉 등록 중 그 인물이 이미 위촉직 3개 이상이면 저장 전에 "이 위촉으로 위촉직이 N개가 됩니다"라는 경고를 보여주되 저장은 허용한다.
- 당연직으로 등록하는 경우에는 경고하지 않는다.
- 다른 위원회의 정보는 위원회명·소관부서·담당자·위원회 내 직위·위촉유형·임기까지만 보여준다.
