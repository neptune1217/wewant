# wewant 개발 계획 — 춘천시 위원회·위원 통합관리 시스템

v2 · 2026-11-13 · 5장의 결정사항 확정 반영. 테이블·필드·계산 규칙의 상세는 `데이터모델.md` 참조.

## 1. 기술스택

한 사람이 AI와 함께 만들고 유지하므로 "언어 하나, 코드베이스 하나, 서버 한 대에 올릴 수 있는 구성"을 기준으로 골랐다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js 16** (App Router, TypeScript, Server Actions) | 화면과 서버 로직이 한 프로젝트에 있어 AI가 전체 맥락을 한 번에 다룬다. |
| DB | **PostgreSQL** | 강하게 연결된 관계형 데이터. 날짜 계산·집계에 강함. |
| ORM | **Prisma ORM 7** (버전 고정) | 스키마 파일 하나가 DB 구조의 단일 기준. |
| 인증 | **Better Auth** (아이디+비밀번호, DB 세션) | 사용자 정보를 내 DB에 보관. 총괄담당자가 계정 발급. |
| UI | Tailwind CSS + shadcn/ui | AI가 가장 일관되게 생성하는 조합. |
| 표/필터 | TanStack Table | 다중 필터와 정렬. |
| 차트 | Recharts | 비율·분포 통계. |
| 엑셀 | ExcelJS (서버에서 생성) | xlsx 내보내기, 일괄 가져오기. |
| 검증 | Zod | 입력 규칙을 화면과 서버가 공유. |
| 테스트 | Vitest, Playwright | 임기·연임·중복위촉·권한 자동 검증. |
| 실행/배포 | Docker Compose (앱 + PostgreSQL) | 개발 PC와 시청 내부망 서버에서 같은 방식으로 실행. |
| 개발 도구 | Claude Code + GitHub(`neptune1217/wewant`) | 단계마다 되돌릴 지점 확보. |

### 설치할 때 주의할 점 (2026-11 기준)
- **Prisma**: `prisma@latest`는 RC 단계인 8을 설치한다. `prisma@7`, `@prisma/client@7`로 고정한다.
- **Next.js 16**: 요청 가로채기 파일 이름이 `middleware.ts`에서 `proxy.ts`로 바뀌었다.
- **인증**: Auth.js(NextAuth)는 유지보수 모드. Better Auth의 아이디 로그인 설정은 설치 시점의 공식 문서를 확인해 진행한다.

### 운영 전제
운영 위치는 시청 내부망이다. 현재는 프로토타입이므로 **가상 데이터만** 사용한다(예시 엑셀의 데이터도 모두 가상). 실제 데이터 투입 전에 정보보안 담당 부서와 보안성 검토·접속기록 보관 등을 협의한다.

## 2. 데이터베이스

원본 8개 테이블 구조를 유지하고 아래를 바꾼다. 상세는 `데이터모델.md`.

- 예시 엑셀 TB_Pos의 `person_id` 오타(`u…` → `p…`)를 시드에서 바로잡는다.
- 활성화 필드명을 `_activ`로 통일하고 boolean으로 저장한다.
- TB_User에 로그인 아이디·비밀번호 해시·최초 비밀번호 변경 여부를 추가한다.
- TB_Appoint: `appoint_end`는 실제 해촉일만 저장하고, 만료 예정일(`expire_due`), 위촉 구분(`appoint_kind`), 종료 사유(`end_reason`)를 추가한다.
- TB_Pos에 (인물, 기관, 직위) 고유 제약을 두고, 참조 중인 행은 수정하지 않는다.
- TB_AccessReq(열람 요청), TB_AuditLog(변경 이력)를 새로 만든다.
- 삭제는 비활성화로 처리한다.

## 3. 권한 설계

| 기능 | 총괄(r01) | 부서(r02) |
|---|---|---|
| 조직·사용자·위원회직위명 관리 | 전체 CRUD | 불가 (사용자정보는 본인 것만 열람) |
| 위원회 | 전체 CRUD | **본인이 담당자(`mng_user_id`)인 위원회만** CRUD |
| 위촉(위원 명부) | 전체 CRUD | 본인 담당 위원회만 CRUD |
| 타 담당자 위원회 상세 | 열람 가능 | 요청 → 담당자가 기간(일)을 정해 승인 → 기간 내 열람만 |
| 인물 | 전체 CRUD | 등록·조회 가능. 수정은 그 인물의 위촉 건이 모두 본인 담당 위원회에 있을 때만 |
| 소속직위 | 전체 CRUD | 새 행 추가 가능. 본인 담당 위촉 건이 가리키는 행을 교체 가능 |
| 중복위촉 조회 | 가능 | 가능(최소 정보) |
| 통계 | 가능 | 가능(집계 수치만) |
| 엑셀 내보내기 | 전체 | 열람 권한이 있는 범위만 |

같은 부서 동료라도 담당자가 아니면 편집할 수 없다. 담당자 변경(인사이동 인계)은 총괄이 처리한다.

구현 원칙: 권한 판정은 `permissions.ts` 한 파일의 함수로만 하고, 모든 서버 동작이 이 함수를 거친다.

## 4. 바이브코딩 순서

각 단계는 "브랜치 하나 → AI에게 계획 먼저 요청 → 구현 → 완료 기준 확인 → 커밋"으로 진행한다.

### 0단계 — 준비 ✅
- `CLAUDE.md`, `docs/개발계획.md`, `docs/데이터모델.md` 작성, 결정사항 확정
- 남은 일: Node.js LTS·Git·Docker Desktop·Claude Code 설치 확인, 폴더를 GitHub 저장소와 연결

### 1단계 — 프로젝트 뼈대와 DB
- Next.js 프로젝트 생성, Docker Compose로 PostgreSQL 실행
- `데이터모델.md`대로 Prisma 스키마 작성 → 마이그레이션
- 예시 엑셀을 읽어 넣는 시드 스크립트(오타 수정, `appoint_end`의 미래 날짜는 `expire_due`로 옮김)
- 완료 기준: Prisma Studio에서 10개 테이블과 예시 데이터가 관계대로 조회됨

### 2단계 — 로그인과 권한 골격
- 로그인 화면, 로그인 후 공통 레이아웃과 4개 탭(홈 / 위원회·위원 / 통계 / 사용자정보)
- 세션, 비활성 사용자 차단, 최초 로그인 시 비밀번호 변경
- `permissions.ts`와 단위 테스트
- 완료 기준: 총괄·부서 계정 로그인 가능, 비로그인 접근 시 로그인 화면으로 이동, 권한 테스트 통과

### 3단계 — 기준정보 관리 (총괄 전용)
- 부서(국소–부서 계층), 사용자, 위원회 내 직위명 CRUD
- 목록·폼·다이얼로그의 공통 화면 패턴을 여기서 확정해 이후 재사용
- 완료 기준: 부서 계정은 주소를 직접 입력해도 접근 거부

### 4단계 — 위원회 관리
- 목록(검색, 소관부서·설치유형·운영형태 필터), 상세, 등록·수정·비활성화
- 부서 계정은 본인 담당만 편집, 타 담당은 목록에 기본 정보만 표시
- 완료 기준: 담당자가 아닌 계정의 수정 요청을 서버가 거부

### 5단계 — 인물·소속직위·위촉 (핵심)
- 위원회 상세의 **위원 명부**: 재임/해촉, 소속직위, 위원회 내 직위, 위촉유형, 위촉일, 만료 예정일, D-day, 연임횟수
- 업무 흐름: **신규 위촉**(인물 검색 → 없으면 등록 → 소속직위 선택/추가 → 위촉 정보), **해촉**, **연임**, **위원회 내 직위 변경**, **소속직위 변경**(위촉 건의 `pos_id` 교체)
- 계산 함수는 순수 함수로 분리하고 테스트를 먼저 작성
- 정원 초과, 연임 가능횟수 초과 시 경고
- 완료 기준: 계산 테스트 통과(윤년, 보궐, 임기 중 직위변경, 연임 0회 위원회 포함). **한 인물을 두 위원회에 서로 다른 소속직위로 위촉한 뒤 한쪽을 바꿔도 다른 쪽이 그대로인지 확인**

### 6단계 — 중복위촉 조회와 경고
- 성명(+생년월일) 검색 → 전체 위원회 소속 현황과 위촉직 건수
- 위촉직 4개 이상 인물에 경고 아이콘 표시(명부·조회 화면 공통), 신규 위촉 저장 전 경고(차단하지 않음)
- 완료 기준: 동명이인 구분, 당연직은 건수에서 제외, 4번째 위촉직이 경고와 함께 저장됨

### 7단계 — 열람 요청·승인
- "열람 요청" → 담당자 홈에 표시 → 열람 기간(일)을 정해 승인 또는 거절 → 기간 내 읽기 전용 열람
- 완료 기준: 승인 전·거절·기간 만료 후에는 상세가 보이지 않고, 만료 후에는 재요청해야 함. 승인 중에도 수정 불가

### 8단계 — 필터와 엑셀 내보내기
- 필터: 출생연도 범위, 성별, 위촉유형, 연임횟수, 위해촉 상태, 위원회, 부서
- 현재 필터 결과를 xlsx로 다운로드(서버에서 권한 재확인, 이력 기록)
- 완료 기준: 화면 건수와 엑셀 행 수 일치, 열람 권한 없는 위원회의 위원은 미포함

### 9단계 — 홈 대시보드와 만료 알림
- 내 담당 위원회 요약: 성별 비율, 공무원/민간 비율, 정원 대비 현원
- 임기만료 D-60 이내 대상자(D-30, D-7 강조), 처리 대기 중인 열람 요청
- 완료 기준: D-61은 안 보이고 D-60부터 보임

### 10단계 — 통계
- 범위(춘천시 전체 / 국소 / 부서) → 위원회 수, 위원 수, 성별·공무원/민간·위촉유형·연령대 분포
- 완료 기준: 차트 수치가 같은 조건의 DB 집계 결과와 일치

### 11단계 — 사용자정보 탭
- 부서 계정: 본인 정보 열람, 비밀번호 변경. 총괄: 사용자 관리
- 완료 기준: 부서 계정이 다른 사용자 정보에 접근하면 거부

### 12단계 — 기존 엑셀 일괄 가져오기
- 표준 양식 다운로드 → 작성 → 업로드 → 오류 행 미리보기 → 확정 반영
- 완료 기준: 오류 행이 사유와 함께 표시되고 정상 행만 반영

### 13단계 — 점검과 배포
- Playwright 권한 시나리오(총괄/부서A/부서B), 로그인 시도 제한, 세션 만료, DB 백업, 운영용 Docker Compose, 운영 매뉴얼
- 완료 기준: 새 PC에서 문서만 보고 `docker compose up`으로 실행됨

### 진행 원칙
- 한 번에 한 단계. 구현 전에 계획을 받는다.
- 규칙은 테스트로 고정한다. 이후 단계에서 테스트가 깨지면 즉시 멈춘다.
- 단계마다 커밋. 꼬이면 직전 커밋으로 되돌리고 다시 요청한다.
- 스키마를 바꿀 때는 `데이터모델.md`와 `CLAUDE.md`도 함께 고친다.

## 5. 확정된 결정사항 (2026-11-13)

1. **본인 소관** = 위원회 담당자(`mng_user_id`) 한 사람.
2. **중복위촉**: 위촉직 3개까지가 원칙이나 예외가 있으므로 입력을 차단하지 않는다. 위촉직 4개 이상인 인물은 경고 아이콘으로 표시한다. 당연직은 세지 않는다.
3. **위원회별 소속직위**: 위촉 건이 인물의 특정 소속직위 행을 가리키고, 변경은 그 위촉 건의 참조만 교체한다. 다른 위원회의 표시는 영향받지 않는다.
4. **임기만료일** = 위촉일 + 임기년수 − 1일 (2026-10-01, 2년 → 2028-09-30).
5. **열람 승인**: 승인자가 열람 기간을 1일 단위로 정한다. 만료 후에는 다시 승인받아야 한다.
6. **운영 위치**: 시청 내부망. 프로토타입 단계에서는 가상 데이터만 사용.
